## ЧАСТЬ 1: ОБЩЕЕ (OVERVIEW)

### 1.1. Что за проект

**Project Glossy Noise** — уютный, но жуткий аналоговый хоррор с элементами глубокого симулятора ремонта электроники в эстетике Y2K.

**Жанр:** Analog Surreal Horror / Cozy Indie Horror / 2.5D Repair Simulator
**Движок:** Godot 4.7 (GDScript, Forward Plus, Jolt Physics)
**Разработчик:** phantasmaWorks
**Сеттинг:** Полуподвальная мастерская-квартира 2005 года в аномальной панельной застройке ([[Гигабреж]]), переплетённой с [[Наукоградом]].

**Ключевая фишка:** Тактильность — не «одна из фишек», а главный геймплейный клей. Игрок физически считывает вращение мыши при выкручивании винтов, ведёт паяльник по дорожкам, оттирает налёт ватной палочкой. Каждое действие ощущается весомым, аналоговым и честным.

### 1.2. Ключевые элементы

- **Core Loop:** Разборка → Чистка → Диагностика → Пайка → Сборка → Отправка по пневмопочте.
- **Хоррор:** Не скримеры, а густая атмосфера, звуковая паранойя, сюрреализм и клаустрофобия.
- **Нарратив:** Через диалоги виртуального ассистента [[Глитчи]] (CRT-монитор), письма в ОС, странные происшествия в подъезде.
- **Экономика:** Заработок на ремонте → оплата аренды [[Управдом]]у → апгрейды инструментов и мастерской.
- **Стресс:** Шкала 0–100, растёт от работы с аномальной техникой, ночных шумов, ТВ-аномалий. Сбрасывается перекуром, пивом, микроволновкой, выполненными заказами.
- **Атмосфера:** Crunchy Y2K / Dither-punk / Лиминальный Y2K. Контраст между уютом рабочего стола и пугающей темнотой.

## ЧАСТЬ 3: РЕСУРСЫ И ДАННЫЕ

### 3.1. Архитектура данных (Resource-based System)

Вся балансная и контентная логика отвязана от скриптов взаимодействия. Используется встроенная в Godot система `Resource` — `.tres` файлы.

**Папки ресурсов:**
res://resources/  
├── devices/ # DeviceData.tres — девайсы  
├── faults/ # FaultData.tres — поломки  
├── dialogues/ # GlitchieDialogue.tres — диалоги Глитчи  
├── items/ # ItemData.tres — предметы маркета  
└── mails/ # MailData.tres — письма


### 3.2. Структуры ресурсов

**`DeviceData.gd`** (`extends Resource`, `class_name DeviceData`)

| Поле | Тип | Назначение |
|------|-----|------------|
| `device_id` | String | Уникальный ключ (напр. `"pager_silencer"`) |
| `display_name` | String | Название для UI |
| `model_scene` | PackedScene | Ссылка на 3D-сцену девайса |
| `base_reward` | int | Базовая выплата за ремонт |
| `is_anomalous` | bool | Флаг аномальности |
| `difficulty` | int | Сложность (1–5 звёзд) |
| `possible_faults` | Array[FaultData] | Список возможных поломок |

**`FaultData.gd`** (`extends Resource`, `class_name FaultData`)

| Поле | Тип | Назначение |
|------|-----|------------|
| `fault_id` | String | Уникальный ключ (напр. `"dead_battery"`) |
| `fault_name` | String | Название для UI |
| `required_tool` | String | Какой инструмент нужен (`"screwdriver"`, `"soldering_iron"`) |
| `repair_steps` | Array[String] | Шаги ремонта (`["open_cover", "replace_battery"]`) |
| `penalty_for_ignore` | int | Штраф (стресс), если проигнорировать |
| `stress_on_error` | int | Стресс при ошибке в ремонте |

**`GlitchieDialogue.gd`** (`extends Resource`, `class_name GlitchieDialogue`)

| Поле | Тип | Назначение |
|------|-----|------------|
| `dialogue_id` | String | Уникальный ключ (напр. `"default"`) |
| `phrases_low_stress` | Array[String] | Фразы при стрессе 0–30% |
| `phrases_mid_stress` | Array[String] | Фразы при стрессе 31–70% |
| `phrases_high_stress` | Array[String] | Фразы при стрессе 71–100% |
| `anomalous_reactions` | Array[String] | Реакции на аномалии |
| `rename_refusals` | Array[String] | Фразы-отказы при переименовании |
| `repair_success` | Array[String] | Реакции на успешный ремонт |
| `repair_fail` | Array[String] | Реакции на неудачный ремонт |

### 3.3. ResourceManager — как грузит

`ResourceManager` (автолоад) в `_ready()` сканирует папки `devices/`, `faults/`, `dialogues/` и грузит все `.tres` в три словаря. Ключ — строковый ID из самого ресурса (`device_id`, `fault_id`, `dialogue_id`).

**Методы:**
- `get_device(device_id) -> DeviceData` — с fallback `null` + `print`
- `get_fault(fault_id) -> FaultData`
- `get_dialogue(dialogue_id) -> GlitchieDialogue`
- `get_all_device_ids() -> Array`
- `get_random_device() -> DeviceData` — равновероятный выбор

**Важно:** `items` и `mails` **не грузятся здесь** — они грузятся в `MarketManager` и `MailManager` соответственно. Архитектура менее централизована, чем в GDD, но работает.

### 3.5. Планируемые MVP-девайсы (из GDD / Дорожной карты)

На текущем этапе приоритет отдаётся трём базовым девайсам для отработки цикла:

3. **Электронные часы** — аномальный: обратный отсчёт к «00:00» провоцирует агрессивный стук в дверь.

### 3.6. Архитектурное решение: отдельные сцены для девайсов

**Утверждено:** каждый девайс — отдельная сцена `.tscn` (не одна общая с подменой меша).

**Почему:**
- Визуально разные меши и коллайдеры.
- Разная логика (калькулятор, часы, пейджер).
- На 5+ девайсах одна сцена превратится в монстра с `if device_id == ...`.

**Структура (план):**
scenes/devices/  
├── pager.tscn ([device.gd](https://device.gd/) + [pager.gd](https://pager.gd/))  
├── calculator.tscn ([device.gd](https://device.gd/) + [calculator.gd](https://calculator.gd/))  
└── clock.tscn ([device.gd](https://device.gd/) + [clock.gd](https://clock.gd/))

**Связь:** `DeviceData.model_scene: PackedScene` — ссылка на сцену. `OrderSpawner` инстанцирует `device_data.model_scene.instantiate()`.

**Наследование:** базовый `device.gd` — общая логика (винты, крышка, гнездо, сборка, отправка). Наследники (`pager.gd`, `calculator.gd`, `clock.gd`) — уникальная логика аномалий.

### 3.7. Архитектурное решение: IncomingTube

**Утверждено:** анимация вылета девайса из трубы — отдельный узел `IncomingTube`, не часть `order_spawner`.

**Почему:**
- Разделение ответственности: `OrderSpawner` — «когда и что», `IncomingTube` — «как анимировать».
- Переиспользование.
- По GDD: «Входящая труба: девайс со звуком грохота и анимацией `EASE_OUT_BOUNCE` вываливается на стол + частицы пыли».

**План:**
workbench_v_2.tscn  
├── OrderSpawner (только выбор девайса и таймер)  
├── IncomingTube (анимация вылета + частицы + звук)  
└── PneumoTube (исходящая, уже есть)

## ЧАСТЬ 4: MVP-СОСТОЯНИЕ, ЗАГЛУШКИ И АРХИТЕКТУРНЫЕ ДОЛГИ

### 4.1. Что работает (проверено)

**Core Loop (ремонт пейджера):**
1. Откручивание 4 винтов → инвентарь.
2. Авто-сдвиг крышки → открытие платы и гнезда.
3. Клик по гнезду → вставка батарейки → `is_repaired = true`.
4. Клик по крышке → возврат на место.
5. Закручивание 4 винтов из инвентаря → `is_assembled = true`.
6. Клик по пневмотрубе → отправка девайса → `+$50`.

**Мета-системы:**
- GameManager: время суток (4 фазы), стресс, деньги, заказы.
- Inventory: 6 слотов, добавление/удаление.
- ResourceManager: загрузка `.tres`.
- GlitchieManager: диалоги, реакции на стресс, `try_rename()` с пасхалками.
- MailManager: 6 писем, панель в ОС.
- MarketManager: 3 товара, покупка → списание денег → инвентарь.
- PC: toggle ОС, блокировка 3D-кликов.
- MoneyDisplay: Label3D с балансом + анимация.
- OrderSpawner: таймер 2.5 сек после сдачи заказа.
- ТВ-аномалия: случайный триггер, рост стресса.
- Смена суток: День → Вечер → Ночь → Глубокая ночь.

### 4.3. Известные баги (помечены, не срочно)

**1. Стресс режется до int.**
`GameManager.stress: int`, но `add_stress(amount: float)` делает `int(amount)`. Дробные приросты (0.1, 0.5) теряются. В DAY (0.1) и EVENING (0.5) стресс **вообще не растёт**. Это противоречит балансу из дорожной карты.

**Фикс (один из двух):**
- Поменять `stress: int` → `stress: float`, округлять только для UI.
- Или умножить все значения на 10 (0.1 → 1, 0.5 → 5) и делить на 10 при отображении.

**2. Расхождение порогов Глитчи.**
`GlitchieManager._get_stress_phrase()`: пороги 50/70.
`GlitchieDialogue.gd` (комментарии): 0–30 / 31–70 / 71–100.
Расхождение на границе 30–49: `GlitchieManager` отдаёт `phrases_low_stress`, хотя по ресурсу должен `phrases_mid_stress`.

**Фикс:** либо поправить `GlitchieManager` на 30/70, либо обновить комментарии в ресурсе.

**3. Рассинхрон `visible` и счётчика винтов.**
`screws_installed` в `device.gd` меняется вручную, а `visible` — отдельно. Могут рассинхрониться.

**Фикс:** считать `screws_installed` через `visible` при каждой проверке, или связать их в одном месте.

**4. `DialogLabel` — warning в редакторе.**
В `workbench_v_2.tscn` у `DialogLabel` висит warning. Скорее всего, missing resource или неправильный тип. Надо глянуть.

### 4.4. Архитектурные долги (на будущее)

**1. Хардкод путей в скриптах.**
`click_manager.gd`: `get_node("../Device")`, `get_node_or_null("../PC")`, `get_node_or_null("../PneumoTube/FunnelPos")`.
`pc.gd`, `GlitchieManager.gd`: `OSPanel/DialogLabel`, `OSPanel/NameEdit`.

**Риск:** при переименовании/переструктурировании сцены — всё сломается.
**Фикс:** `@export` переменные или `get_meta()` / группы.

**2. `_get_mesh_parent()` — эвристика с «братом StaticBody3D».**
Работает под текущий паттерн (`MeshInstance3D` + `StaticBody3D` как соседи). Хрупко.

**Фикс (при интеграции арта):** либо сохранить паттерн, либо перейти на `get_meta("mesh")` / группы.

**3. `_get_inventory()` / `_get_game_manager()` — поиск по имени с `to_lower()`.**
Костыль вместо `get_node("/root/Inventory")`. Медленнее и хрупко.

**Фикс:** прямой путь, раз автолоады глобальные.

**4. `ResourceManager._load_all_resources` — не рекурсивный.**
Если в `resources/devices/` появятся подпапки — не загрузятся.

**Фикс:** рекурсия или явные пути.

**5. `ResourceManager.load()` — синхронный.**
На MVP — ок. Когда будет 50+ девайсов — `ResourceLoader.load_threaded_request`.

**6. Нет обработки дубликатов ID в ресурсах.**
Два `.tres` с одинаковым `device_id` — второй молча перезапишет первый.

**7. `print` на каждый чих.**
`GameManager`, `click_manager`, `device`, `order_spawner`, `pc`, `GlitchieManager` — везде отладочные принты. На релизе засрут консоль.

**Фикс:** обернуть в `if OS.is_debug_build()`.

**8. `GlitchieManager.try_rename` — `await create_timer(2.5)` без проверки.**
Если игрок закроет ОС или введёт новое имя — таймер всё равно сбросит `NameEdit.text`.

**9. `click_manager` не обрабатывает `event.pressed == false`.**
Hold-механики (удержание ЛКМ, peek, сопротивление двери) — не реализованы. Отложены.

**10. `TimeOfDay` используется только в `GameManager`.**
UI, шейдеры, спавнеры пока не подписаны на `time_changed`. В планах.

## ЧАСТЬ 6: КОНТЕКСТ ДЛЯ АРТА И ЗВУКА

### 6.1. Визуальный стиль: Crunchy Y2K

**Полное название:** Стилизованный Лиминальный Y2K / Crunchy Y2K / Dither-punk с элементами экспрессионизма (vibe Hello Neighbor).

**Ключевая идея:** Утрированные, выразительные 3D-формы и бытовой уют нулевых, контрастирующие с полупрозрачными неоновыми гаджетами. Мягкий градиентный дизеринг сохраняет читаемость зоны верстака, сгущаясь в атмосферную пиксельную тревогу по краям кадра.

**1. Формы и геометрия (Тактильный экспрессионизм):**
- Искривлённый быт: геометрия слегка «неправильная», утрированная.
- Пузатый CRT-телевизор с длинными антеннами, массивные тумблеры, накренённые косяки дверей.
- Все предметы на верстаке имеют выразительные, «уютные» формы.

**2. Смягчённый градиентный дизеринг (Читаемость 10/10):**
- Локальный дизеринг: пиксельная сетка теней и зернистость **не перекрывают весь экран**.
- Зона верстака: рендер чёткий и стилизованный (чтобы не утомлять зрение при пайке).
- Краевые эффекты: дизеринг, хроматические аберрации и CRT-искажения сгущаются по краям кадра, в тёмных углах и при росте стресса.

**3. Контраст палитр («Грязь и Неон»):**
- Фон (суррогатный быт): матовые, шероховатые текстуры полуподвала (болотно-зелёная краска, ржавчина, пыльный бетон, канифоль на деревянном столе).
- Акценты (Y2K-эстетика): кислотный неон CRT-мониторов, свечение Глитчи, полупрозрачный фиолетовый/зелёный пластик гаджетов.

**4. Освещение:**
- Густой тёплый свет от одинокой лампы накаливания сверху.
- Глубокие объёмные тени, мягкий контраст между уютом рабочего стола и пугающей темнотой в проёмах.

### 6.2. 3D-пайплайн (Blender → Krita → Godot)

**Текущий этап (2.5):**
- Инструменты: Blender (модели), Krita (текстуры).
- Подход: комбинирование (Vertex Color + UV + Trim Sheet).

**Порядок моделирования:**
1. Стол + полка (Vertex Color).
2. Пневмотруба (UV + металл).
3. CRT-монитор (UV + экран).
4. Радио (UV + ручки).
5. MVP-девайсы (UV + текстуры).

**Важные технические моменты:**
- **Jolt Physics:** выбран вместо дефолтной физики Godot. Причины:
  - Тактильность и juice: винты, крышки, батарейки должны физично падать.
  - Стабильность микро-коллайдеров (винты, зазоры 1 мм).
  - Пневмотруба и мусоропровод: плотные соударения и импульсы.
  - Задел под аномалии и перформанс: 20+ RigidBody3D без просадки FPS.
- **Паттерн интерактивных объектов:** `MeshInstance3D` + `StaticBody3D` (соседи). Если менять — предупредить DeepSeek (сломается `click_manager._get_mesh_parent()`).
- **Коллизии:** слой `default` (1), `screw` (2), `cover` (3), `socket` (4), `tube` (5). Пока в `click_manager` используется `0xFFFFFFFF` (всё), но слои заложены.

## ЧАСТЬ 7: КАК ОБНОВЛЯТЬ ПАСПОРТ + CHANGELOG

### 7.1. Правила ведения паспорта

**1. Только фрагментарные правки.**
Не перезаписываем весь файл. Обновляем конкретный блок.
- Ты говоришь: «Обнови раздел X в AI_CONTEXT».
- DeepSeek выдаёт **только этот блок**.
- Ты вставляешь в нужное место.

**2. Когда обновлять:**
- При значимых изменениях в архитектуре кода (новый автолоад, новый ключевой скрипт).
- При добавлении/изменении структур ресурсов.
- При закрытии этапа (обновить Часть 5 — Roadmap).
- При появлении новых архитектурных долгов или багов (Часть 4).
- При изменении воркфлоу или ролей (Часть 1).

**3. Когда НЕ обновлять:**
- Мелкие правки баланса (они в GDD / Дорожной карте).
- Косметические изменения UI.
- Багфиксы, не меняющие архитектуру.

**4. Как использовать в новом чате:**
- Кинуть `AI_CONTEXT.md` первым сообщением.
- Добавить: «Продолжаем разработку GlossyNoise. Контекст в паспорте. Текущая задача: [НОМЕР И НАЗВАНИЕ ПУНКТА ИЗ ПЛАНА]».
- DeepSeek прочитает — и в контексте за 30 секунд.

**5. Связь с другими доками:**
- `AI_CONTEXT.md` — сжатый паспорт для ИИ.
- `GDD.md` — полная библия проекта.
- `Дорожная карта.md` — план по этапам.
- `Девлог.md` — хроника сессий.
- `Архитектура.md` — план архитектуры (некоторые скрипты ещё не реализованы).

**6. Версионирование:**
- Каждое крупное обновление — новая версия.
- Changelog — в конце этого файла.
- Формат: `vX.Y (дата) — краткое описание`.
